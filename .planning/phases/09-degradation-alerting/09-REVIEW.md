## Warnings

### WR-08: Интеграционный тест отпечатков — PID-суффикс без очистки БД даёт флаки на переиспользуемых PID и засоряет операторскую таблицу

**File:** `tests/integration/alerts-fingerprint.test.ts:15,43`
**Issue:** Суффикс уникальности скоупов — `process.pid.toString()` (строка 15: `const run = process.pid.toString();`), а `afterAll` только отключает клиента (строка 43: `afterAll(async () => prisma?.$disconnect())`) — созданные строки `OpsAlert` не удаляются. Тесты 1 и 3 ассертят `outcome.action === "open"` / `"re-open"` на первой вставке, поэтому при (а) переиспользовании PID в последующем запуске против той же БД (PID-рециклинг реален и на Windows, и на Linux) или (б) параллельных шарах CI с общим `DATABASE_URL` и совпавшими PID тест ложно падает: первая вставка вернёт `occurrence`/`re-open`. Дополнительно тест оставляет в операторской БД синтетические OPEN-алерты, включая сигнал `WEBHOOK_FAILED`, которого нет в закрытом наборе сигналов воркера, — они видны оператору до авто-разрешения тикером (сигнал `WEBHOOK_FAILED` воркером никогда не порождается и не разрешится никогда — строки-мусор остаются навсегда).
**Fix:** Заменить PID на случайный суффикс запуска, либо явная очистка созданных отпечатков в `afterAll` (если триггеры неизменяемости не блокируют удаление):

```ts
import { randomUUID } from "node:crypto";
const run = randomUUID().slice(0, 8); // уникально для каждого запуска процесса
```

Для строк-мусора `WEBHOOK_FAILED`: не использовать несуществующий сигнал (например, `PROVIDER_QUOTA` с уникальным скоупом) или добавить cleanup созданных `dedupFingerprint`.

### IN-06: Phantom requirement — «синхронность» зеркала сепаратора в веб-приложении ничем не гарантирована и поведенчески не нужна; инъективность U+001F утверждена в комментарии, но не закреплена тестом

**File:** `apps/web/app/internal/operations/alerts-block.tsx:47-53`
**Category:** necessity
**Issue:** Комментарий к `DEDUP_KEY_SEPARATOR` требует, чтобы константа «оставалась синхронной с воркером, чтобы два домена дедупликации не разошлись молча», но (а) никакого теста, закрепляющего значение веб-константы, нет (grep по репозиторию — упоминание только в самом файле и planning-артефактах), и (б) само требование — фантомное: ключ используется исключительно внутри одной отрисовки `AlertsBlock` (`alerts-block.tsx:109-115`) и никогда не пересекает границу модуля, поэтому любое константное значение сепаратора даёт идентичное поведение дедупликации (прежний `\0` в памяти работал безупречно — смена в 09-07 чисто косметическая). Дрейф этой константы не может изменить поведение. Сопутствующий пробел: утверждение в `workers/data-sync/src/jobs/alerts.ts:62-70`, что U+001F «никогда не встречается внутри provider/endpoint scope», тоже ничем не закреплено (нет теста на инъективность для произвольных скоупов, источники скоупов — конфиг/коды провайдеров, не пользовательский ввод, поэтому риск практически нулевой).
**Fix:** Либо добавить двухстрочный дрейф-гард в `alerts-block.test.ts` (импорт воркер-константы недоступен из web-дерева — тогда статически закрепить ожидаемое значение `\u001f`), либо честно переформулировать комментарий: зеркало — документационное, дрейф поведенчески безопасен. Для воркера — тест-инвариант «ни один из закрытых сигналов и ни один форматированный скоуп не содержит U+001F».

### IN-07: Мёртвое ожидание `waitForTimeout(100)` в zoom-тесте G-09-2

**File:** `tests/e2e/operator-overview.spec.ts:55`
**Issue:** `element.style.zoom = "200%"` применяется синхронно, и последующий `page.evaluate` читает метрики reflow уже после синхронного пересчёта раскладки — фиксированный сон 100 мс не добавляет надёжности, только время (паттерн, который Playwright документирует как анти-пат). При будущем ускорении прогона это место останется балластом.
**Fix:** Удалить `await page.waitForTimeout(100)`; при необходимости устойчивости — заменить на `await expect(page.locator("html")).toBeVisible()` либо оставить прямой замер без сна.

### IN-08: В фикс-коммит 0a03eeb, заявленный как закрытие G-09-1/G-09-2, контрабандно внесён несвязанный рестайл `<summary>`, не отражённый ни в покрытии 09-07-SUMMARY, ни в сообщении коммита

**File:** `apps/web/app/globals.css:177-194`
**Issue:** Диф `globals.css` в диапазоне содержит полную переработку стилей `<summary>` (акцентный цвет, подчёркивание, шеврон через `::before`/`details[open]`), тогда как коммит `0a03eeb` декларирует только «quota-counter min-width:0, overflow-wrap», а `09-07-SUMMARY.md:114` перечисляет лишь «quota-counter min-width: 0 at <=480px; overflow-wrap/min-width:0 for block containers». Изменение затрагивает каждый `<details>` сайта (в том числе секцию «Неудачные задачи» на странице операций, `page.tsx:105`) и не покрыто ни одним тестом плана 09-07 — заявленное покрытие фазы не соответствует фактическому дифу.
**Fix:** Отразить изменение в SUMMARY/плане (дописать строку покрытия) или вынести рестайл в отдельный коммит при будущих фикс-коммитах; для шеврона достаточно визуальной проверки — но она должна быть зафиксирована как охваченная.

### IN-09: Спред `ACK_CHIP` в inline-style утекает не-CSS ключ `dot` в проп `style`

**File:** `apps/web/app/internal/operations/alerts-block.tsx:142`
**Issue:** `style={{ ...ACK_CHIP, background: ACK_CHIP.bg, border: ..., color: ... }}` — спред приносит ключ `dot` (значок чипа, не CSS-свойство) в объект стилей; в dev-режиме React логирует предупреждение о неподдерживаемом свойстве, в production молча игнорирует. Избыточен вдвойне: `background`/`border`/`color` тут же переопределяются явно, из спреда реально нужен только `dot` — то есть его как раз быть не должно. Пре-существующий код (не из дифа 09-07), обнаружен при сплошном чтении файла.
**Fix:** Убрать спред, оставив явные поля:
`style={{ fontSize: "0.875rem", background: ACK_CHIP.bg, border: `1px solid ${ACK_CHIP.border}`, color: ACK_CHIP.color, borderRadius: "9999px", padding: "2px 10px" }}`
