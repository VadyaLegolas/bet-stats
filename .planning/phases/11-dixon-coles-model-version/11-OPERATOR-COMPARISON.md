# Операторское сравнение V1 и Dixon-Coles

Команда `scripts/model-comparison.mjs` (npm-скрипт `pnpm model:compare`) подаёт два rolling-origin плана — `poisson-ensemble-v1` и `dixon-coles-ensemble-v1` — на **одних и тех же окнах**, ждёт воркер и печатает квитанцию `model-comparison-v2`. Закрывает UAT-пункт 2 фазы 11.

Квитанция информационная: модель **не продвигается автоматически**, дефолт `dixon-coles-ensemble-v1` не меняется, результаты прошлых матчей не гарантируют будущих.

Этот документ описывает процедуру и фактическое поведение команды. Числовых результатов сравнения здесь нет: квитанцию реальной когорты оператор получает сам, а её запись в UAT делает `/gsd-verify-work`.

## Почему CLI-скрипт, а не эндпоинт

- Подача планов — запись плюс постановка в очередь; оператору нужен контроль диапазона и параметров, а не публичный HTTP-вход. Скрипт не расширяет поверхность API и не требует eligibility-заголовков.
- Образец в репозитории: `scripts/seed-configured-leagues.mjs` (операторский скрипт над БД). Логика вынесена в `workers/data-sync/src/jobs/model-comparison.ts` и `model-comparison-cli.ts`, поэтому покрыта тестами; `.mjs` только подключает зависимости.
- Квитанция строится тем же кодом, что и `GET /evaluation/model-comparison` (`compareBacktestPlans` + `toModelComparisonResult`), а эндпоинт остаётся рабочим (см. ниже).

## Предусловия

1. Собранный проект: после любых правок кода выполните `pnpm build` перед `node scripts/model-comparison.mjs` — скрипт использует `dist`, а не исходники.
2. Миграции применены к той БД, на которой идёт сравнение. Миграция `20261123_phase11_settlement_chain_per_forecast` действует на уровне базы, а не `dist`: пересборка её не доставляет. Перед `run` примените миграции к используемой (лучше к копии) БД:

   ```powershell
   $env:DATABASE_URL = "<строка подключения к копии БД>"
   pnpm --filter @bet-stats/database exec prisma migrate deploy
   ```

   Без миграции DC-план падает на первом же окне с `settlement revision must link predecessor`: цепочка ревизий оценки там ещё общая для матча, и второй прогноз того же матча не может встать в неё.
3. Запущен воркер `data-sync` (он исполняет планы из очереди; для DC ρ фитится на `trainingEndsAt` каждого окна).
4. Переменные окружения: `DATABASE_URL`, `REDIS_URL`, при нестандартном префиксе очереди — `QUEUE_PREFIX` (как у воркера).
5. Node 24.

**Предупреждение о записи.** Бэктест пишет `ForecastSnapshot`, `SettlementReceipt` и `ForecastScore` в те же append-only таблицы, что и рабочая система; удалить эти строки штатно нельзя. Для репетиции используйте копию БД, а не рабочую базу.

## Одна команда

```powershell
node scripts/model-comparison.mjs run --from 2026-08-01T00:00:00Z --to 2026-11-01T00:00:00Z --league league-pl,league-pd
```

Что происходит:

1. По `FINISHED`-матчам диапазона строятся окна. Матч попадает в когорту только если к `evaluationAsOf` известен его результат и для **обеих** команд есть опубликованные (`PUBLISHED`) билды доказательств на **точную** отсечку. Отсечка — момент матча минус лид; лид по умолчанию 6 ч, как у production `PRE_MATCH`. Граница обучения (там фитится ρ) на 24 ч раньше прогноза, знание результата — через 48 ч после матча; эти два лага не менялись.
2. На один момент отсечки остаётся один матч — с наименьшим `id`; остальные матчи с тем же моментом считаются пропущенными. Сдвигов отсечки нет: каждая отсечка равна моменту матча минус лид ровно, потому что только на этот момент существует билд доказательств. Окна строго возрастают по `forecastCutoff`.
3. Подаются два плана с `configHash = forecastConfigHashFor(modelVersion)` через `admitPersistEnqueueBacktest` и BullMQ.
4. Скрипт ждёт `SUCCEEDED` у обоих (по умолчанию до 30 минут) и печатает квитанцию.

Параметры: `--market ONE_X_TWO|OVER_UNDER_2_5|BTTS`, `--concurrency 1..4`, `--cutoff-hours`, `--training-lag-hours`, `--evaluation-lag-hours`, `--allow-small-cohort`, `--timeout-minutes`, `--dry-run`, `--json`. Не более 500 окон и 365 суток (лимиты `BACKTEST_LIMITS`); при превышении сузьте диапазон или лиги.

`--cutoff-hours` менять не нужно: билды доказательств строятся на отсечку production-лида, и при другом значении у большинства матчей не окажется билда на нужный момент. Значение по умолчанию совпадает с production.

Коды выхода: `0` — квитанция получена, `1` — недоступна, план упал или подача остановлена, `2` — вышло время ожидания.

## Отчёт когорты и минимум

И `--dry-run`, и подача (`run`, `submit`) сначала печатают отчёт когорты:

| Поле | Смысл |
|------|-------|
| `considered` | сколько `FINISHED`-матчей диапазона рассмотрено |
| `usable` | сколько окон получилось |
| `skipped.noResultByEvaluationAsOf` | результат неизвестен к `evaluationAsOf` |
| `skipped.noPublishedEvidenceAtCutoff` | нет опубликованных билдов доказательств обеих команд на точную отсечку |
| `skipped.sharedCutoffInstant` | проиграл тай-брейк на общем моменте отсечки |
| `leadHours` | лид, по которому считались отсечки |
| `minimumRequired` | минимум политики (`MODEL_COMPARISON_POLICY.minimumSampleSize`, 30) |
| `tieBreak` | правило тай-брейка: `smallest-fixture-id` |

Проверки идут в этом порядке: матч, не прошедший раннюю проверку, не занимает место в тай-брейке. Отбор не читает ни исходов, ни метрик, поэтому не смещает сравнение.

Если пригодных окон меньше минимума политики, подача **останавливается до записи** (ничего в БД и очередь не попадает, код выхода `1`). Если окон нет вовсе — то же самое, причина `COMPARISON_NO_ELIGIBLE_FIXTURES`; ниже минимума — `COMPARISON_COHORT_BELOW_MINIMUM`. Флаг `--allow-small-cohort` разрешает заведомо малую когорту: подача идёт с предупреждением, а вердикт будет `INCONCLUSIVE` по построению. `--dry-run` показывает отчёт и пару планов, ничего не записывая (код `1`, если подача невозможна).

Пример на данных UAT 2026-11-23: 130 `FINISHED`-матчей в диапазоне, 110 с доказательствами на момент матча минус 6 ч, 57 различных моментов отсечки — ожидаемо 57 окон. Число зависит от БД оператора; это пример, а не гарантия, и на реальных данных он не прогонялся.

## Параллельность и порядок подачи

`run` подаёт оба плана сразу и ждёт. Последовательная подача не вводится, и это сознательное решение:

- Backtest-воркер работает с `concurrency: 1` (`createBacktestWorker`), поэтому задания берутся по одному в порядке очереди: сначала V1, затем DC.
- Реальная конкуренция в системе — у settlement-воркера (`createSettlementWorker`, `concurrency: 2`). Цепочки ревизий оценки принадлежат **прогнозу**, а не матчу (миграция 11-05), а расчёт ревизии идёт под advisory-lock матча. Поэтому два прогноза одного матча, V1 и DC, оцениваются независимо: у каждого своя `SettlementReceipt` revision 1 и свои `ForecastScore`.
- Последовательная подача добавила бы вторую ветку ожидания в CLI и скрыла бы, а не доказала инвариант, который обеспечивает БД. Его проверяют `tests/integration/settlement-multi-forecast.test.ts` (конкуренция двух прогнозов одного матча) и сквозной тест ниже.

## Идемпотентность

Идентификаторы планов (`cmp-<хэш>-poisson`, `cmp-<хэш>-dixon-coles`) выводятся из параметров и набора окон. Повтор с теми же параметрами и тем же набором завершённых матчей не создаёт дубликатов: `createPlan` возвращает существующий план, а идентификатор задания в очереди детерминирован (`planId` + `planHash`). Если за время между запусками завершились новые матчи или появились новые билды доказательств, набор окон меняется и подаётся новая пара. Флаг `--allow-small-cohort` в идентичность не входит. `--market` тоже не входит: обе модели считают оценки по всем трём рынкам, рынок лишь выбирает, что читает `compare`, поэтому `run --market BTTS` после `run --market ONE_X_TWO` переиспользует те же планы. В идентичность входят хеши конфигурации обеих моделей и `--concurrency` (он часть `planHash`): после смены конфигурации модели подаётся новая пара, а не `BACKTEST_PLAN_ID_CONFLICT`. Изменение версии 11-REVIEW WR-12: идентификаторы пар, подававшихся раньше, не совпадут с новыми. Старые планы остаются в БД и читаются командами `status` и `compare` по их идентификаторам; повторный `run` создаст новую пару.

**Сбои и повтор.** Упавшее окно получает состояние `FAILED`, а задачу очередь повторяет (3 попытки, экспоненциальная пауза). `run` объявляет отказ только когда задача исчерпала попытки, а не при первом упавшем окне. Если задача окончательно упала, повторный `run` или `submit` с теми же параметрами ставит её заново: готовые окна не пересчитываются, упавшие выполняются снова, а CLI сообщает, какие планы перезапущены.

## По шагам

```powershell
node scripts/model-comparison.mjs submit --from 2026-08-01T00:00:00Z --to 2026-11-01T00:00:00Z
node scripts/model-comparison.mjs status --left cmp-<хэш>-poisson --right cmp-<хэш>-dixon-coles
node scripts/model-comparison.mjs compare --left cmp-<хэш>-poisson --right cmp-<хэш>-dixon-coles --from 2026-08-01T00:00:00Z --to 2026-11-01T00:00:00Z
```

В `compare` значения `--from`, `--to` и `--market` должны совпадать с подачей: по ним отбираются оценки.

## Как читать вердикт

- Минимум выборки — `MODEL_COMPARISON_POLICY.minimumSampleSize` (30 исходов), порог существенности по Brier — 0.002.
- Выборка меньше 30 → всегда `INCONCLUSIVE`: это «нет доказательства», а не «DC не хуже V1».
- **Ограничение ρ = 0.** Пока в БД меньше 300 пулированных pre-match снимков (150 на лигу) с известным результатом, ρ фитится как 0 (`insufficient-sample-zero` в `receipt.receipt.dixonColes.method`), и DC численно совпадает с V1. Поэтому первое сравнение на такой базе честно даёт `INCONCLUSIVE` с нулевыми дельтами Brier и logLoss. Это зафиксированное «нет доказательства», а не «DC не хуже»: сравнивать, по сути, нечего. На dev-БД UAT 2026-11-23 как раз такая ситуация (ρ = 0 у всех снимков DC).
- Что делать дальше — решает оператор: расширить историю прогнозов и результатов (больше завершённых матчей с прогнозами) и повторить сравнение. Автоматического продвижения модели нет и не будет.
- `WORSE` — валидный результат; он публикуется как есть и не скрывается. `BETTER` тоже ничего не включает сам: переключение модели остаётся ручным решением.
- `available: false` с причиной (`PLAN_NOT_COMPLETE`, `COHORT_MISMATCH`, ...) — тоже честный ответ, а не вердикт.

## Через HTTP (по готовым планам)

```powershell
curl.exe -sS -G "$env:API/evaluation/model-comparison" `
  --data-urlencode "leftPlanId=cmp-<хэш>-poisson" --data-urlencode "rightPlanId=cmp-<хэш>-dixon-coles" `
  --data-urlencode "market=ONE_X_TWO" --data-urlencode "from=2026-08-01T00:00:00.000Z" --data-urlencode "to=2026-11-01T00:00:00.000Z" `
  -H "x-operator-credential: $env:OPERATOR_CREDENTIAL" -H "x-eligibility-region: <разрешённый регион>" `
  -H "x-age-acknowledged: true" -H "x-eligibility-checked-at: <текущий ISO-момент>"
```

Без `x-operator-credential` ответ — 404.

## Тесты

- `tests/unit/model-comparison-operator.test.ts` — окна, лимиты, идемпотентная подача, ожидание, честный текст при малой выборке.
- `tests/integration/backtest-model-comparison.test.ts` — реальные PostgreSQL и Redis: пара планов на идентичных окнах, повтор без дубликатов, `PLAN_NOT_COMPLETE` до работы воркера, остановка на когорте ниже минимума.
- `tests/integration/backtest-model-comparison-e2e.test.ts` — сквозной путь оператора: `run` со значениями по умолчанию, настоящий backtest-воркер, оркестратор, расчёт оценок и билды доказательств; 32 окна, матч с общим моментом начала, матч без билда на точную отсечку; квитанция `model-comparison-v2`, `INCONCLUSIVE` с нулевыми дельтами при ρ = 0. Подтверждённо красный без миграции 11-05 и на старом CLI.
- `tests/integration/settlement-multi-forecast.test.ts` — два прогноза одного матча оцениваются независимо, в том числе при конкуренции.
- `tests/integration/settlement-chain-upgrade.test.ts` — миграция цепочки ревизий безопасно обновляет заполненную БД.
