## Что сделано

- **WR-05.** `calibratorContentId` покрывает входы подгонки, а не результат. Идентификатор не менялся (старые строки остаются валидными). `persistCalibrator` при дубликате читает сохранённую строку и сравнивает `calibratorContentDigest` (всё, кроме `fittedAsOf`; канонический JSON, поэтому порядок ключей jsonb не важен) с новой подгонкой. Расхождение: `CALIBRATOR_CONTENT_MISMATCH`, запись не меняется. Повторная подгонка тех же данных не даёт ложного срабатывания (проверено на реальном jsonb).
- **WR-01.** Запрет «того же калибратора» остался. Добавлено правило семейства: если в журнале рынка есть `ROLLED_BACK`, кандидат (первое продвижение и замена откатанного к предшественнику) продвигается, только когда среди его отложенных исходов, ставших известными строго после последнего отката, не меньше `minimumSamples.holdout` (60), он опережает откатанный калибратор не меньше чем на `materiality` и не хуже сырого прогноза на эту величину. Любое неизвестное число: отказ (`CANDIDATE_NOT_PROVEN_AFTER_ROLLBACK`). Правило перестаёт действовать, когда активен калибратор, продвинутый после отката. Политика чистая (`rollbackLineageApplies`, `assessRollbackLineage`, `decideCalibrationLifecycle`); поле `rollbackLineage` в `LifecycleCandidate` обязательное, забыть его нельзя. Порог берётся из `calibration-config-v1`, поэтому новая конфигурация не создавалась (v1 заморожена). Жёсткой гарантии в триггере БД нет: БД не может считать Brier, а структурную часть (тот же `calibratorId`) триггер уже проверяет. Текст карточки модели описывает реальное правило.
- **WR-02.** Каждый рынок изолирован. Падение подгонки или применения сохранённого калибратора фиксируется в `failures` квитанции рынка (только коды, без текста сообщений), решение об откате считается всё равно. Сбой рынка целиком не останавливает остальные. После обработки всех рынков при наличии сбоев задание падает с `CALIBRATION_MARKET_FAILED` и приложенной квитанцией, поэтому очередь повторяет его, а сбой виден.
- **WR-03.** Выбран вариант «атомарно»: `rollbackWithEvaluation` пишет EVALUATED и ROLLED_BACK одной транзакцией под одной блокировкой. После сбоя нет ни одного события, повтор считает то же окно и откатывает.
- **WR-04.** Структурное разделение выбора и продвижения (fit / selection / holdout) требует новой политики, то есть `calibration-config-v2`, поэтому в этой правке сделан только честный текст в ограничениях карточки модели.
- **WR-06.** `readCalibrationState` читает активные калибраторы первыми и делает полную перепись, только если у какого-то рынка калибратора нет (для активного рынка `eligibleSampleSize = null`, потребитель его не читает). В API добавлен ограниченный (32 записи) TTL-кеш по точной идентичности: `CALIBRATION_STATE_CACHE_TTL_MS`, по умолчанию 60 с, максимум 300 с, `0` выключает; общие запросы делят одно чтение, ошибки не кешируются. Продвижение или откат видны не позднее TTL. Чтения идентичностей одного запроса идут параллельно.
- **WR-07.** `attachMarketCalibration` сообщает о каждом сбое (раз на идентичность и запрос) через необязательный `onError`: стадия, идентичность и код/имя класса ошибки без текста. Сервис пишет структурную запись уровня warn через Nest `Logger`. Ответ клиенту не менялся.
- **WR-08.** Подтверждено по коду: API показывает калибратор по идентичности самого прогноза (подмены нет), а `assertCalibrationIdentity` отклоняет только вручную поставленные в очередь старые пары (тик ставит только текущие). Реальная дыра: калибратор старого `configHash` остаётся активным, его никто не оценивает, и об этом нигде не видно. Квитанция задания получила `retiredIdentities` (тот же `modelVersion`, другой хэш, рынки), задание пишет warn-событие; сбой этой проверки задание не роняет. Ничего не оценивается, не откатывается и не скрывается.
- **WR-09.** Новый интеграционный тест запускает `startCalibrationRuntime` без `dependencies` на Postgres и Redis в отдельных контейнерах: тик с подставным временем ставит две идентичности, настоящий worker выполняет `execute` и `runCalibrationJob`, DC даёт 3 продвинутых калибратора, V1 даёт `INSUFFICIENT_DATA`. Регулярное выражение для `start()` в `calibration-job.test.ts` оставлено: `start()` не экспортируется и стартует только при прямом запуске.

## Требуют решения (needs-decision)

1. **WR-04: разделить выбор метода и отложенную выборку продвижения.** Варианты: (a) оставить оговорку (сделано); (b) `calibration-config-v2` с тремя окнами fit / selection / holdout (новые фиксированные доли, перевычисление метрик, ломает сопоставимость Brier между версиями); (c) оценивать выбранный метод на последних N исходах, не участвовавших в сравнении (меньше отложенная выборка, N в конфигурации v2). Нужно решение владельца, так как меняется D-05/D-07 (политика и пороги).
2. **WR-08: жизненный цикл ушедших идентичностей.** Варианты: (a) только отчёт (сделано); (b) в API возвращать `UNAVAILABLE` с новым кодом `IDENTITY_RETIRED` для идентичностей вне текущих (меняет закрытый набор кодов, текст UI и семантику старых матчей); (c) тик ставит и ушедшие идентичности с активным калибратором, пока по ним поступают исходы, чтобы они оценивались и откатывались (снимает проверку `assertCalibrationIdentity` для таких пар и меняет D-10). До решения старые прогнозы продолжают показывать «Калибровка v{n}» ушедшей идентичности, но теперь это видно в квитанции и журнале.
3. **WR-02: автоматический откат структурно повреждённого активного калибратора.** Сейчас это зафиксированный сбой `EVALUATION/CALIBRATOR_INVALID`: API показывает `UNAVAILABLE`, остальные рынки работают, задание падает и повторяется, но откат не происходит (калибратор не прошёл гистерезис D-10). Варианты: (a) оставить; (b) прямой `ROLL_BACK` с кодом `CALIBRATOR_INVALID` без гистерезиса (расширяет закрытый набор причин отката и обходит D-10 для класса «битые параметры»).
