<objective>
Prove the whole 7-day value scanner architecture end to end on its thinnest path, then pin the read model's semantics on a real PostgreSQL: one `VALUE_CANDIDATE` receipt travels from the database through the single-statement window query, the new `GET /value/scanner` endpoint and the server-rendered `/scanner` page with its stored edge and EV strings unchanged.

Purpose: SCAN-01 (consolidated forward-looking list with fixture, market, selection, edge, EV, odds source), SCAN-02 (verbatim stored values, freshness computed once by the API, EMPTY summary data) and SCAN-03 (no N+1) all depend on this read model; the public endpoint contract (D-03, costly to change) is fixed here so Plans 15-02..15-05 build on a proven slice.

Output: domain scanner module, API repository/service/controller, a thin page, seed helpers, and an integration suite on a disposable PostgreSQL container.

Recorded assumptions (researcher recommendations adopted, visible to every later plan): (1) freshness is measured from `ManualOddsSnapshot.submittedAt` per D-06; the DTO also carries an informational `oddsCapturedAt` that never feeds the calculation. (2) A flag for "odds replaced by a newer book" is out of scope and goes to deferred ideas. (3) No `internal-api/scanner` proxy route is created: the page calls the API directly like `apps/web/app/scorecards/page.tsx`. (4) Truncation is at a fixture boundary. (5) DTO names follow the code, not the pre-code UI-SPEC wording: `valuePolicyVersion`, `competition` is `League.name`, `evPolicyVersion` exists only for Asian handicap receipts. (6) Freshness thresholds confirmed for `scanner-freshness-v1`: 6 h and 24 h; FRESH below 6 h, AGING from 6 h through 24 h inclusive, STALE above 24 h. Schema gate: no schema file or migration is in scope (D-13), so no database push task is injected; if a measurement ever shows an index is required it becomes a separate direct migration with its own plan.
