<objective>
Fix review finding WR-13 (`.planning/phases/11-dixon-coles-model-version/11-REVIEW.md`, evidence in `11-REVIEW-FIX.md` section "Skipped Issues / WR-13"): the operator model comparison publishes retrospective forecasts through the same `publish` as production, and the public scorecard reads every `forecastScore` without provenance. On the e2e database (no production forecast at all) the public cohort `all/all/ONE_X_TWO` returned 32 fixtures, 64 forecasts, 192 events, all from backtests.

Purpose: the product's core value is honest, measurable probability quality. A public scorecard that silently contains retrospective forecasts (issued after the match, multiplied per model) is not honest.

Output: a forward-only migration adding `ForecastSnapshot.origin` (PRODUCTION | BACKTEST), the write path that tags backtest publications, public readers restricted to PRODUCTION, a recorded and tested decision for the Dixon-Coles rho fit, regression tests on real PostgreSQL, updated review documents, and a phase 11 backlog note.

Sizing note: the user fixed a 3-task structure. Task 2 touches many files but each is a one-line `origin: "PRODUCTION"` filter of the same shape, so it is kept as one task. Tests are placed with the code they cover (tasks 1 and 2) so every commit is green on its own; task 3 holds the real-database regression tests, mutation proofs and documents.

<decisions>
User decisions, already fixed (locked, do not revisit):
- D-01: `ForecastSnapshot.origin` enum `PRODUCTION | BACKTEST`, NOT NULL, default `PRODUCTION`, added by a forward-only Prisma migration; existing rows become `PRODUCTION`; update `schema.prisma` and regenerate the Prisma client.
- D-02: Backtest publication (the backtest and model-comparison publish path) creates NEW snapshots with origin `BACKTEST`. When the snapshot identity collides with an existing snapshot, return that existing snapshot unchanged; never mutate or re-label a production snapshot.
- D-03: Public readers (`findIssued`, `listIssued`, `loadCohort`, and any other scorecard or public forecast read, including value candidates and `enumerateAvailableCohorts`) select only origin `PRODUCTION`. Backtest-internal readers (backtest windows, backtest scoring and settlement) keep seeing BACKTEST snapshots where they do today.
- D-04: Decide with evidence whether the Dixon-Coles rho fit (`packages/database/src/dixon-coles-repository.ts` `collectRows`, and the WR-04 residual) excludes BACKTEST snapshots; plan the change with a test or a recorded reason, and put the decision in the SUMMARY. (Decided below: exclude.)
- D-05: Tests: (a) a regression integration test that fails without the fix and passes with it: after a model-comparison run on a database with no production forecast, public `loadCohort('all')` returns nothing from backtest; (b) a test that a V1 backtest hitting an existing production snapshot identity leaves it PRODUCTION and public.
- D-06: Update the WR-13 disposition in `11-REVIEW.md` and `11-REVIEW-FIX.md`; record the out-of-scope `valueByFixture` issue (loses values when a fixture has several settlement receipts; changes `valueReceiptId` in published events) in a phase 11 backlog note.
- D-07: Out of scope: the pre-existing SQLSTATE 40001 serialization failures on parallel settlement of different fixtures.

D-04 decision (planner, under the user's delegation) and its evidence:
- `collectRows` filters `state ISSUED`, `kind PRE_MATCH`, `cutoff < asOf`, `issuedAt <= asOf` and the fixture window, with no provenance. A backtest snapshot has `cutoff = kickoff - lead` and `issuedAt` = wall-clock time of the run (`ForecastOrchestrator.run` sets `issuedAt: new Date().toISOString()`).
- Every backtest fit uses `asOf = window.trainingEndsAt` (`resolveDixonColes` in `workers/data-sync/src/main.ts` and in the e2e test). WR-04's `issuedAt <= asOf` therefore already excludes later-written backtest snapshots from every backtest and comparison fit, so excluding BACKTEST rows changes nothing for backtests or the comparison receipt.
- A production forecast fits at `asOf` = its own cutoff, close to now (`resolveDixonColes` in `forecast-orchestrator.ts` passes `input.asOf`). Those fits do include backtest snapshots, so an operator running a comparison over any range silently changes rho for later live forecasts, and the output of a backtest feeds the live model that the same scorecard then scores. That is the WR-04 residual recorded in `11-REVIEW.md`.
- Decision: exclude BACKTEST from the fit (`origin: "PRODUCTION"` in the `collectRows` snapshot filter) and cover it with a test. It is a one-line, reversible change. Counter-argument recorded, not adopted: backtest rows could bootstrap a rho fit on a young database; if wanted that must be a deliberate feature with explicit provenance (deferred-items.md candidate), not a side effect of an operator command. Known residual: backtest snapshots written BEFORE this migration are labelled PRODUCTION by D-01 and keep feeding fits at `asOf` = now.
</decisions>
