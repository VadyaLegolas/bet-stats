# Football Prediction & Value Betting Platform — Спецификация

## 1. Цель проекта

Создать веб-приложение для автоматического анализа ближайших футбольных матчей топ-5 европейских лиг и еврокубков, расчёта вероятностей футбольных событий и поиска потенциальных value-bet возможностей.

Приложение не должно обещать выигрыш. Оно должно оценивать вероятности и сравнивать их с рыночными коэффициентами.

## 2. Поддерживаемые турниры

- Premier League
- La Liga
- Serie A
- Bundesliga
- Ligue 1
- UEFA Champions League
- UEFA Europa League (см. ограничение источников данных, п.3)
- Опционально: UEFA Conference League (см. ограничение источников данных, п.3)

Список турниров должен задаваться через конфигурацию.

## 3. Источники данных и fallback-стратегия

Для MVP используются только бесплатные тарифы. **Реальные ограничения free-тарифов (проверено на 2026 год) существенно уже, чем кажется на первый взгляд, поэтому стратегия описана честно, а не оптимистично.** Ниже — не два источника, а карта ролей: у каждого источника есть чётко ограниченная зона ответственности, и смешивать их нельзя.

### 3.1 Основной источник fixtures/standings — football-data.org Free
- Лимит: 10 запросов/минуту.
- Покрывает 12 турниров: топ-5 лиг + Champions League + ряд других. **Europa League и Conference League в бесплатный список НЕ входят.**
- Lineups, детальная статистика и odds — платные add-on'ы, недоступны бесплатно.
- Роль: **prod**, основной источник fixtures/standings для топ-5 лиг + ЧЛ.

### 3.2 Резервный источник fixtures/lineups — API-Football Free
- Лимит: ~100 запросов/сутки.
- Доступно бесплатно: fixtures, standings, teams, lineups (после подтверждения).
- **Не гарантировано на free-тарифе**: injuries, odds, predictions, детальная statistics — в прайсинге провайдера эти данные относятся к платным тарифам (Pro и выше). Приложение обязано программно проверять `coverage`-флаги перед вызовом эндпоинта и не считать эти данные доступными по умолчанию.
- Роль: **prod**, резерв для топ-5+ЧЛ и основной источник fixtures/lineups для Europa League / Conference League (которые football-data.org не покрывает).

### 3.3 Нормализация сущностей — TheSportsDB Free
- Лимит: 30 запросов/мин (тестовый ключ), данные community-driven — точность ниже, чем у прод-источников.
- Роль: **entity-aid, не источник статистики**. Используется только для слоя `TeamExternalRef`/`PlayerExternalRef` (см. п.14) — в базе TheSportsDB много альтернативных написаний имён команд, что упрощает fuzzy-matching между football-data.org и API-Football. Логотипы команд — тоже отсюда.
- Не использовать как источник live-статистики или результатов матчей.

### 3.4 xG и продвинутая статистика — три разных роли, не путать
- **Understat** — xG/PPDA по топ-5 лигам. Это не официальный API: данные встроены в JSON внутри HTML-страницы, доступ через неофициальный scraping. Роль: **caution** — использовать только с явным rate-лимитом, кэшированием и пониманием, что доступ может быть заблокирован в любой момент; не делать обязательной зависимостью MVP.
- **FBref** — с января 2026 года потерял лицензию на данные Opta: **текущие/live advanced-stats (xG и т.п.) больше не обновляются**, только исторический архив остаётся полным. Роль: **historical-only** — годится для обучения/валидации модели на прошлых сезонах, но не для live-фич текущего сезона.
- **StatsBomb Open Data** (GitHub, JSON, официальные Python/R пакеты) — событийные данные высочайшего качества с xG, но покрывает только отдельные исторические соревнования и сезоны (не live топ-5 лиг текущего сезона). Роль: **training-only** — калибровка и бэктестинг Poisson/Elo модели на эталонных данных, не встраивается в prod-пайплайн.

### 3.5 Следствия для продукта (важно)
1. Europa League / Conference League при отказе основного источника **не остаются совсем без данных** — они переключаются на API-Football (см. п.3.2), но это не работает в обратную сторону (если недоступен API-Football, у EL/UECL нет резерва). Явно показывать пользователю статус "ограниченные данные" для этих турниров при деградации API-Football.
2. Injuries и odds не следует проектировать как "автоматически получаемые бесплатно" — де-факто в MVP это будет либо отсутствовать, либо основываться на ручном вводе пользователя. Ручной ввод odds — не fallback, а основной механизм в MVP.
3. Перед каждым запросом к API-Football проверять объект `coverage` для конкретной лиги/сезона, чтобы не тратить бюджет запросов на заведомо недоступные эндпоинты.
4. Источники из п.3.3–3.4 не входят в DailyApiBudget (п.13) прод-пайплайна: TheSportsDB имеет собственный отдельный бюджет как entity-aid сервис, а training-only/caution источники (FBref, StatsBomb, Understat) не вызываются синхронно при обработке live-матчей вообще — только офлайн, отдельными джобами вне пользовательского пути.

Запрещено делать обязательной частью MVP:
- платные API;
- платные xG-провайдеры;
- платные odds-провайдеры;
- scraping, нарушающий Terms of Service источника.

## 4. Основные функции

Система должна:

1. находить ближайшие матчи;
2. сохранять матчи в PostgreSQL;
3. собирать историю последних матчей команд;
4. рассчитывать форму за 5 и 10 матчей;
5. отдельно учитывать домашнюю и выездную форму;
6. рассчитывать Elo-рейтинг;
7. учитывать H2H с небольшим весом;
8. учитывать травмы, дисквалификации и отсутствующих игроков **только если данные подтверждены coverage-флагом источника или введены вручную**;
9. использовать официальные составы, когда они доступны;
10. рассчитывать вероятности через Poisson + Elo + форму;
11. поддерживать рынки 1X2, Double Chance, Over/Under и BTTS;
12. получать коэффициенты **преимущественно через ручной ввод пользователя** (см. п.3.5);
13. рассчитывать implied probability, edge и expected value;
14. сохранять immutable prediction snapshots;
15. выполнять backtesting после завершения матчей;
16. показывать результаты в React/Next.js интерфейсе;
17. сопоставлять сущности (команды, игроки, матчи) между провайдерами данных, чтобы переключение на резервный источник не создавало дублей (см. п.14).

## 7. Weighted Form

Последние матчи получают больший вес.

Пример:
- матч -1: 1.00
- матч -2: 0.90
- матч -3: 0.80
- матч -4: 0.70
- матч -5: 0.60

## 8. Prediction Engine V1

Базовая модель:

Poisson + Elo + Recent Form + Home/Away Strength + H2H + Missing Players

Poisson рассчитывает lambdaHome и lambdaAway, затем строит матрицу вероятностей счёта минимум от 0:0 до 7:7.

Из неё выводятся:
- Home / Draw / Away;
- 1X / X2 / 12;
- Over/Under 1.5;
- Over/Under 2.5;
- Over/Under 3.5;
- BTTS Yes/No;
- team totals.

## 9. Value Bet Engine

Для decimal odds:

`impliedProbability = 1 / odds`

Для многовариантных рынков необходимо нормализовать вероятности, чтобы убрать bookmaker overround.

Базовый метод MVP — мультипликативная нормализация (сумма вероятностей делится на сумму implied probabilities). Он прост, но искажает оценку в пользу фаворитов/аутсайдеров (favorite-longshot bias). Для V2 стоит предусмотреть более точный метод устранения overround (например, Shin's method или power method) как конфигурируемую опцию `oddsNormalizationMethod`.

`edge = modelProbability - marketProbability`

`EV = modelProbability * odds - 1`

Рекомендуемый фильтр по умолчанию:
- Edge >= 5%
- EV > 0

## 10. Confidence Score

Confidence не равен вероятности события.

Диапазон: 0–100.

### 10.1 Компоненты и формула

Confidence должен рассчитываться как явная взвешенная сумма, а не оставаться качественным описанием:

```
confidence =
    dataCompletenessScore   * 0.30  +
    lineupConfirmedScore    * 0.25  +
    dataFreshnessScore      * 0.20  +
    sourceReliabilityScore  * 0.15  +
    modelStabilityScore     * 0.10
```

Где:
- `dataCompletenessScore` (0–100) — доля обязательных полей, фактически заполненных для этого матча;
- `lineupConfirmedScore` — 100, если состав подтверждён (LINEUP_CONFIRMED snapshot), 40 если только прогнозируемый, 0 если недоступен;
- `dataFreshnessScore` — убывает по мере устаревания данных относительно kickoff (шкала задаётся конфигом);
- `sourceReliabilityScore` — берётся из `DataQualityLog` (см. схему БД, п.14) по конкретному провайдеру;
- `modelStabilityScore` — исторический разброс (variance) прогнозов той же версии модели на схожих матчах.

Веса должны быть вынесены в конфигурацию, а не захардкожены — они будут калиброваться по мере накопления backtesting-данных.

## 11. Prediction Snapshots

Прогнозы нельзя изменять задним числом.

Типы snapshot:
- INITIAL
- PRE_MATCH
- LINEUP_CONFIRMED
- FINAL

Каждый snapshot содержит capturedAt.

## 12. Backtesting

После завершения матчей рассчитывать:
- Brier Score;
- Log Loss;
- Accuracy;
- Calibration;
- ROI;
- Yield;
- CLV, если доступна история коэффициентов.

Все тесты должны предотвращать data leakage.

## 13. API Budget

Цель: меньше 100 внешних запросов в день (лимит именно API-Football Free, football-data.org считается отдельно, по 10 запросов/минуту).

Бюджет должен вестись **по провайдеру и по типу эндпоинта отдельно** (fixtures, results, lineups, injuries, odds, misc), а не одной общей цифрой — иначе приоритизация из ARCHITECTURE.md нечем enforce'ить программно.

Приоритет обновлений:
1. fixtures;
2. результаты;
3. составы перед матчем;
4. травмы (если coverage подтверждён);
5. odds (если coverage подтверждён; иначе ручной ввод);
6. второстепенная статистика.

Исторические данные кэшируются в БД и повторно не загружаются без необходимости.

## 14. Entity Matching и Fixture Reconciliation

Так как основной и резервный источники присваивают одной и той же команде/игроку/матчу разные внешние ID, простое поле `provider + externalId` на самой сущности **создаёт дубликаты** при переключении между источниками. Поэтому:

- Team и Player хранятся как канонические сущности; привязка к конкретному провайдеру выносится в отдельные таблицы `TeamExternalRef` / `PlayerExternalRef` (см. schema.prisma).
- При получении данных от нового провайдера сначала выполняется поиск существующего канонического Team/Player по имени + стране (fuzzy match), и только при отсутствии совпадения создаётся новая каноническая запись.
- Для матчей (Fixture) реконсиляция выполняется по паре (canonical homeTeamId, canonical awayTeamId, дата в окне ±36 часов) — если запись с такими параметрами уже существует от другого провайдера, новый externalId привязывается к тому же Fixture, а не создаёт дубль.
- Все решения по сопоставлению логируются (кто с кем был сопоставлен и почему) для возможности ручной проверки в админке.

## 15. Legal, Ethical и Responsible Gambling требования

- Приложение не гарантирует прибыль ни в каком виде текста интерфейса, уведомлений или маркетинга; формулировки — только "вероятностная оценка", "аналитический прогноз".
- На каждом экране с прогнозом — постоянный дисклеймер о рисках ставок и вероятностной природе прогноза.
- MVP не выполняет автоматическую постановку ставок и не интегрируется с букмекерскими API для исполнения.
- Возрастные ограничения и доступность функции ставок должны учитывать юрисдикцию пользователя (конфигурируемый флаг региона).
- Использование источников данных должно соответствовать их Terms of Service; scraping вне ToS запрещён.
- Персональные данные пользователя (сохранённые матчи, история прогнозов) хранятся с учётом требований приватности; отдельного согласия требует хранение поведенческих данных, связанных со ставками.
- Self-exclusion / лимиты активности — вне MVP, зафиксировать в Roadmap как будущую фичу.

## 17. MVP Definition of Done

MVP готов, когда он автоматически:
1. получает ближайшие матчи;
2. сохраняет их;
3. загружает историю команд;
4. рассчитывает форму;
5. рассчитывает Elo;
6. запускает Poisson;
7. строит вероятности 1X2;
8. строит O/U 2.5;
9. строит BTTS;
10. отображает прогноз в интерфейсе;
11. сохраняет snapshot;
12. получает финальный результат;
13. оценивает качество прошлого прогноза;
14. корректно сопоставляет сущности при переключении между провайдерами (без дублей команд/матчей).
